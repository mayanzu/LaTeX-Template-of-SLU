\subsection{游戏主循环设计}

主循环是经典的"事件处理—状态更新—渲染"三段式。游戏开发里这基本是标准做法\upcite{14}，不花哨，但写的时候踩了不少坑。

核心逻辑在\texttt{main.py}：

\begin{lstlisting}[language=python,caption={游戏主循环核心逻辑}]
while running:
    current_time = pygame.time.get_ticks()
    # 事件处理
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False
        elif event.type == pygame.KEYDOWN:
            handle_key(event.key)

    # 状态更新（基于时间步）
    if game.state == STATE_PLAYING:
        game.update(current_time)

    # 渲染
    screen.fill(COLORS['background'])
    renderer.draw_all()
    pygame.display.flip()
    clock.tick(FPS)
\end{lstlisting}

容易忽略的细节：\texttt{game.update()}的调用时机。直接调不控制时间间隔的话，蛇速会跟CPU主频绑定——快机器上蛇飞，慢机器上蛇爬。所以加了\texttt{move\_delay}参数（默认150ms），用当前时间$t_{now}$和上次移动时间$t_{last}$判断。移动触发条件：
\begin{equation}
	t_{now} - t_{last} \ge T_{delay}
\end{equation}
$T_{delay}$是移动间隔，蛇速（格/秒）：
\begin{equation}
	v_{snake} = \frac{1000}{T_{delay}} \text{ (格/秒)}
\end{equation}
$T_{delay}=150$ms时，蛇速约6.67格/秒。

A*可视化数据的更新频率也做了独立控制（\texttt{ASTAR\_UPDATE\_INTERVAL = 500ms}），不和游戏帧同步。A*搜索量不小，每帧都跑一次帧率会骤降，特别是障碍物密集的时候。500ms更新一次对可视化够了，用户感觉是"实时"的。

\subsection{蛇的数据结构与移动逻辑}

蛇的表示用最朴素的方案——Python列表，每个元素是\texttt{(x, y)}元组，索引0是蛇头。增删都是O(1)\upcite{4}，没什么争议。

移动逻辑在\texttt{snake.py}：

\begin{lstlisting}[language=python,caption={蛇的移动逻辑}]
def move(self, direction=None):
    if direction is None:
        direction = self.direction
    # 防止180度反向
    if self._is_opposite_direction(direction, self.direction):
        direction = self.direction
    self.direction = direction
    dx, dy = DIRECTIONS[direction]
    new_head = (self.head[0] + dx, self.head[1] + dy)
    self.body.insert(0, new_head)
    if self.grow_pending > 0:
        self.grow_pending -= 1
    else:
        self.body.pop()
    return new_head
\end{lstlisting}

方向反向判断可以形式化。设当前方向$\vec{d_c} = (dx_c, dy_c)$，新方向$\vec{d_n} = (dx_n, dy_n)$，反向判定：
\begin{equation}
	\vec{d_c} \cdot \vec{d_n} = dx_c \cdot dx_n + dy_c \cdot dy_n = -1
\end{equation}
四方向移动的方向向量集合$\{(1,0),(-1,0),(0,1),(0,-1)\}$，相反方向的点积都是$-1$。

\texttt{grow\_pending}计数器的设计有个坑。最开始直接往body里append，但食物碰撞检测的时机有问题——蛇头到食物的那帧，同时检测碰撞和增长，顺序搞不好就出bug。用pending计数器把增长延迟到下次move处理，逻辑就干净了。

\subsection{食物与障碍物生成算法}

食物和障碍物都是随机生成，但不能完全随机。蛇头周围3格内不能放障碍物——经验值，太小了开局就卡死，太大了障碍物没意义。

\begin{lstlisting}[language=python,caption={障碍物生成（含安全区保护）}]
def _generate_obstacles(self):
    obstacles = set()
    safe_zone = set()
    for dx in range(-3, 4):
        for dy in range(-3, 4):
            safe_zone.add((self.snake.head[0] + dx,
                          self.snake.head[1] + dy))
    while len(obstacles) < OBSTACLE_COUNT:
        x = random.randint(0, GRID_WIDTH - 1)
        y = random.randint(0, GRID_HEIGHT - 1)
        pos = (x, y)
        if pos not in obstacles and pos not in safe_zone:
            obstacles.add(pos)
    return obstacles
\end{lstlisting}

食物生成要额外避开蛇身和已有障碍物，用\texttt{occupied}集合并集判断。退化情况：蛇身占了绝大部分格子时食物找不到位置。设最大尝试次数100次，还是找不到就判定游戏赢——蛇已经把地图吃满了。

\subsection{碰撞检测机制}

碰撞检测三种情况：撞墙、撞障碍物、撞自己。前两种直接边界检查和集合查找。撞自己这第三种，写的时候犯过迷糊。

问题在时机上。\texttt{game.update()}先调\texttt{snake.move()}，蛇头已经插到\texttt{body[0]}了。所以检测自撞应该查新蛇头是否在\texttt{body[1:]}里，不是\texttt{body[0:]}：

\begin{lstlisting}[language=python,caption={碰撞检测（含自身碰撞）}]
def _check_collision(self, head):
    # 撞墙
    if not (0 <= head[0] < GRID_WIDTH and
            0 <= head[1] < GRID_HEIGHT):
        return True
    # 撞障碍物
    if head in self.obstacles:
        return True
    # 撞自身（排除蛇头）
    if len(self.snake.body) > 1:
        body_set = set(self.snake.body[1:])
        if head in body_set:
            return True
    return False
\end{lstlisting}

还有个坑：\texttt{grow\_pending > 0}时尾巴不pop，蛇头绕到尾巴"原位置"按上面逻辑撞不到（尾巴还留在那）。这个行为其实是对的——吃食物那帧尾巴保留，蛇身实际变长了一格，撞到延长的蛇身应该判死。

\subsection{渲染器设计}

渲染器\texttt{renderer.py}承担所有绘制。渲染和逻辑严格分离——\texttt{Game}不知道自己长什么样，\texttt{Renderer}不知道游戏规则。

网格坐标到屏幕像素的变换：
\begin{equation}
	\begin{cases}
		px = x \cdot cell\_size + offset\_x \\
		py = y \cdot cell\_size + offset\_y
	\end{cases}
\end{equation}
$(x,y)$是网格坐标，$cell\_size$是格子像素大小，$(offset\_x, offset\_y)$是网格区域左上角偏移。反过来像素到网格：
\begin{equation}
	x = \left\lfloor \frac{px - offset\_x}{cell\_size} \right\rfloor, \quad
	y = \left\lfloor \frac{py - offset\_y}{cell\_size} \right\rfloor
\end{equation}

渲染分层从底到上依次画。每层的混合公式：
\begin{equation}
	I_{final}(x,y) = \alpha_l \cdot I_l(x,y) + (1 - \alpha_l) \cdot I_{l-1}(x,y)
\end{equation}
$\alpha_l$是第$l$层透明度，$I_l(x,y)$是该层颜色值。底层深灰\texttt{\#1E1E1E}背景，上面画暗灰\texttt{\#323232}网格线（1像素宽）。然后依次画A*路径预览（半透明蓝线）、灰色障碍物方块、红色食物圆形、绿色蛇身方块（蛇头更亮）。最上层是UI面板半透明黑遮罩和文字，以及右侧A*可视化区域。

A*可视化面板是这个项目比较有意思的部分。右侧400$\times$500像素区域，实时展示搜索过程：绿色起点、红色终点、蓝色已探索、橙色待探索、黄色最终路径。调启发式权重的时候全靠看这个面板判断搜索"方向感"够不够强。

\subsection{双模式切换}

\texttt{M}键切自动和手动模式。

自动模式\texttt{SmartDecisionMaker}每帧算下一步方向。手动模式方向键直接传入\texttt{game.update()}。切换即时生效，不重置游戏。

自动模式决策在\texttt{decision.py}的\texttt{decide\_next\_move()}里，核心是三层降级：

\begin{lstlisting}[language=python,caption={自动模式三层决策降级}]
def decide_next_move(self, snake, food_positions, obstacles):
    # 第一层：A*寻路到最近食物
    path = self.pathfinder.find_path(head, target_food)
    if path and len(path) > 1:
        return self._position_to_direction(head, path[1])
    # 第二层：BFS兜底
    bfs_dir = self._get_bfs_direction(head, target, obstacles)
    if bfs_dir:
        return bfs_dir
    # 第三层：安全评估择优
    return self._get_safe_move_with_prediction(...)
\end{lstlisting}

三层之间有个矛盾：A*给的路径最优但计算量最大；BFS保证能找到路（如果存在）但路径不一定最短；安全评估计算量最小但给不出"到食物"的保证。实测90\%以上情况第一层A*就够了，BFS偶尔用到，安全评估基本是最后保命手段。
