\section{系统详细设计与实现}

本章讨论整个贪吃蛇游戏系统从底层数据结构到上层渲染管线的具体实现。说实话，Pygame不是什么高大上的框架，但它的API够直观，拿来写这种规模的原型完全够用，省得折腾引擎层的东西。

\subsection{游戏引擎与开发环境}

开发语言选了Python 3.x，渲染框架用的Pygame 2.x。做这个选择的时候纠结过一阵子——C++配合SDL2在性能上肯定有优势，但考虑到这个项目的重点在算法而不是引擎优化，Python的开发效率优势就很明显了。写个A*原型，用Python调通逻辑再快不过。

Pygame底层封装的是SDL2，提供窗口管理、事件循环、2D渲染这些基础能力\upcite{19}。对于本项目40$\times$30的网格规模，Pygame的软件渲染完全扛得住，60fps下CPU占用不到15\%（实测数据，i7-12700H）。

\subsection{游戏主循环设计}

游戏主循环采用了经典的"事件处理—状态更新—渲染"三段式结构。这种模式在游戏开发里几乎是标准做法\upcite{14}，没什么花哨的，但写的时候踩了不少坑。

主循环的核心逻辑在\texttt{main.py}里，大致是这样一个骨架：

\begin{lstlisting}[language=python,caption={游戏主循环核心逻辑}]
while running:
    current_time = pygame.time.get_ticks()
    # 事件处理
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False
        elif event.type == pygame.KEYDOWN:
            handle_key(event.key)

    # 状态更新（基于时间步）
    if game.state == STATE_PLAYING:
        game.update(current_time)

    # 渲染
    screen.fill(COLORS['background'])
    renderer.draw_all()
    pygame.display.flip()
    clock.tick(FPS)
\end{lstlisting}

这里面有个容易忽略的细节：\texttt{game.update()}的调用时机。如果把更新逻辑放在事件循环外面直接调，没有时间间隔控制，蛇的移动速度会和CPU主频绑定——在快机器上蛇飞快，在慢机器上蛇蠕动。所以加了一个\texttt{move\_delay}参数（默认150ms），通过比较\texttt{current\_time}和\texttt{last\_move\_time}来控制节奏。

另外，A*可视化数据的更新频率也做了独立控制（\texttt{ASTAR\_UPDATE\_INTERVAL = 500ms}），不和游戏帧同步。原因很简单：A*搜索的计算量不小，每帧都跑一次会让帧率骤降，尤其是障碍物密集的时候。500ms更新一次对可视化来说完全够了，用户看到的是"实时"的感觉。

\subsection{蛇的数据结构与移动逻辑}

蛇的表示用了最朴素的方法——一个Python列表，每个元素是\texttt{(x, y)}元组，索引0是蛇头。这个选择在实现上没什么争议，增删操作都是O(1)的时间复杂度\upcite{4}。

移动逻辑的代码写在\texttt{snake.py}里：

\begin{lstlisting}[language=python,caption={蛇的移动逻辑}]
def move(self, direction=None):
    if direction is None:
        direction = self.direction
    # 防止180度反向
    if self._is_opposite_direction(direction, self.direction):
        direction = self.direction
    self.direction = direction
    dx, dy = DIRECTIONS[direction]
    new_head = (self.head[0] + dx, self.head[1] + dy)
    self.body.insert(0, new_head)
    if self.grow_pending > 0:
        self.grow_pending -= 1
    else:
        self.body.pop()
    return new_head
\end{lstlisting}

方向反向的判断用了一个简单的映射表：\texttt{\{'UP': 'DOWN', 'DOWN': 'UP', ...\}}。这个比计算角度什么的靠谱多了，四方向移动下不会出错。

\texttt{grow\_pending}这个计数器的设计有个坑。最开始的版本是直接往body列表里append，但这样会导致食物碰撞检测的时机问题——蛇头到达食物位置的那帧，如果同时要检测碰撞和增长，顺序搞不好就出bug。用pending计数器把增长延迟到下一次move时处理，逻辑就干净多了。

\subsection{食物与障碍物生成算法}

食物和障碍物的生成都是随机的，但不能完全随机。蛇头周围3格范围内不能放障碍物，这是个经验值——太小了开局就卡死，太大了障碍物形同虚设。

\begin{lstlisting}[language=python,caption={障碍物生成（含安全区保护）}]
def _generate_obstacles(self):
    obstacles = set()
    safe_zone = set()
    for dx in range(-3, 4):
        for dy in range(-3, 4):
            safe_zone.add((self.snake.head[0] + dx,
                          self.snake.head[1] + dy))
    while len(obstacles) < OBSTACLE_COUNT:
        x = random.randint(0, GRID_WIDTH - 1)
        y = random.randint(0, GRID_HEIGHT - 1)
        pos = (x, y)
        if pos not in obstacles and pos not in safe_zone:
            obstacles.add(pos)
    return obstacles
\end{lstlisting}

食物生成时需要额外避开蛇身和已有障碍物，用了个\texttt{occupied}集合做并集。这里有个退化情况：当蛇身占了绝大部分格子时，食物可能找不到可用位置。处理方式是设置最大尝试次数（100次），如果还是找不到就判定游戏胜利——蛇已经把地图吃满了，确实该赢了。

\subsection{碰撞检测机制}

碰撞检测分三种情况：撞墙、撞障碍物、撞自己。前两种好说，就是边界检查和集合查找。撞自己这第三种情况，写的时候犯过迷糊。

问题出在时机上。\texttt{game.update()}里先调\texttt{snake.move()}，此时蛇头已经插到了\texttt{body[0]}位置。所以检测自撞时，应该检查新蛇头是否在\texttt{body[1:]}里，而不是\texttt{body[0:]}：

\begin{lstlisting}[language=python,caption={碰撞检测（含自身碰撞）}]
def _check_collision(self, head):
    # 撞墙
    if not (0 <= head[0] < GRID_WIDTH and
            0 <= head[1] < GRID_HEIGHT):
        return True
    # 撞障碍物
    if head in self.obstacles:
        return True
    # 撞自身（排除蛇头）
    if len(self.snake.body) > 1:
        body_set = set(self.snake.body[1:])
        if head in body_set:
            return True
    return False
\end{lstlisting}

还有一个容易踩的坑：当蛇吃了食物、\texttt{grow\_pending > 0}时，尾巴不会pop。这时候蛇头如果绕到尾巴的"原位置"，按上面的逻辑是撞不到的（因为尾巴已经留在那里了）。这个行为其实是对的——吃到食物那帧尾巴保留，蛇身实际变长了一格，撞到延长的蛇身应该判死。

\subsection{渲染器设计}

渲染器\texttt{renderer.py}承担了所有绘制工作。为了不污染游戏逻辑层，渲染和逻辑是严格分离的——\texttt{Game}类完全不知道自己长什么样，\texttt{Renderer}类完全不知道游戏规则。

渲染分为以下几个层次，从底到上依次绘制。背景使用深灰色\texttt{\#1E1E1E}填充，其上绘制暗灰色\texttt{\#323232}的网格线，宽度为1像素。随后依次绘制A*路径预览的半透明蓝色线条、灰色方块障碍物、红色圆形食物，以及绿色方块蛇身（其中蛇头使用更亮的绿色以示区分）。最上层是UI面板的半透明黑色遮罩和文字信息，以及右侧独立的A*可视化面板区域。

A*可视化面板是这个项目比较有意思的部分。它在游戏窗口右侧开辟了400$\times$500像素的区域，实时展示A*算法的搜索过程：绿色是起点，红色是终点，蓝色是已探索节点（closed set），橙色是待探索节点（open set），黄色是最终路径。这个面板对调试算法参数非常有用——之前调启发式权重的时候，全靠看这个面板判断搜索是否"方向感"够强。

\subsection{双模式切换}

游戏支持自动和手动两种模式，用\texttt{M}键切换。

自动模式下，\texttt{SmartDecisionMaker}每帧计算下一步方向。手动模式下，方向键直接传入\texttt{game.update()}的\texttt{manual\_direction}参数。切换是即时的，不需要重置游戏状态。

自动模式的决策逻辑在\texttt{decision.py}的\texttt{decide\_next\_move()}方法里，核心是三层降级：

\begin{lstlisting}[language=python,caption={自动模式三层决策降级}]
def decide_next_move(self, snake, food_positions, obstacles):
    # 第一层：A*寻路到最近食物
    path = self.pathfinder.find_path(head, target_food)
    if path and len(path) > 1:
        return self._position_to_direction(head, path[1])
    # 第二层：BFS兜底
    bfs_dir = self._get_bfs_direction(head, target, obstacles)
    if bfs_dir:
        return bfs_dir
    # 第三层：安全评估择优
    return self._get_safe_move_with_prediction(...)
\end{lstlisting}

三层降级的设计有个trade-off：A*给出的路径是最优的，但计算量最大；BFS保证能找到路径（如果存在），但路径不一定最短；安全评估函数计算量最小，但给不出"到食物"的保证。实测中，90\%以上的情况第一层A*就够了，BFS兜底偶尔用到，安全评估基本是最后的保命手段。

\subsection{本章小结}

这一章把系统实现中的关键模块过了一遍。核心的设计决策包括：主循环的时间步控制、蛇身的增长延迟机制、碰撞检测的时机处理、渲染层级分离，以及三层决策降级。每个决策背后都有过翻车的经历——特别是碰撞检测那块，debug了差不多一个下午才搞清楚时序问题。
